# myterm 设计

一个 Windows 终端。目标是把「终端」这件事做对：VT 解析交给成熟的库，界面用现代的 Rust 框架，其余全部是自己的代码，且每一层都能单独测试。

## 为什么这样分层

终端应用有三个几乎无关的问题：

1. **字节到网格**。ANSI 序列、宽字符、回滚、选区、按键编码——这是 VT 解析器的工作，细节多且容易出错。
2. **网格到像素**。每个单元格的位置、颜色、装饰线、光标形状。
3. **应用外壳**。标签、分屏、快捷键、配置。

把三者混在一起，任何一处改动都会牵连另外两处。所以分成四个 crate，依赖严格向下：

```
app ──► pty
 │       ▲
 └────► vt ──► vt-sys
```

`vt-sys` 是唯一出现 `unsafe extern "C"` 的地方；`vt` 把指针所有权、错误码、颜色类型全部包装成值；`pty` 只负责进程和管道；`app` 只做界面。这条边界让「解析器崩了」和「界面画错了」永远不会混在同一个栈里。

## VT 层

### 为什么用官方 C API

之前用第三方 Rust 封装，它锁在一个 pre-1.0 的 commit 上，封装本身有近两万行。官方 1.0.0 提供了稳定 ABI 和版本承诺，代价是要自己写绑定。

绑定是手写的：本机没有 `libclang`，`bindgen` 不可用。手写反而更可控——只声明真正用到的约 40 个函数，每个常量都对着头文件核对过。

### 静态库

`libghostty-vt` 用 Zig 构建，官方不发 Windows 包。做法是在 1.0.0 源码上跑：

```sh
zig build -Demit-lib-vt -Doptimize=ReleaseFast
```

把 `zig-out/lib/ghostty-vt-static.lib`（12.5 MB）提交进仓库。这样构建机不需要 Zig、不需要网络、不需要 CMake。`build.rs` 只做两件事：检查文件在不在，然后告诉 cargo 链接它。

### sized struct

C API 里所有输出结构体第一个字段是 `size_t size`，库用它判断调用方编译时的结构体版本。Rust 侧不能靠 `derive(Default)`——那会把 `size` 置零，库会拒绝写入。每个这样的结构体都手写 `Default`，显式填 `size_of::<Self>()`。

这个坑在写测试时立刻暴露了：光标位置读出来永远是 0，因为 `GhosttyRenderStateCursor::default()` 的 `size` 是 0。

### 渲染状态

`RenderState` 是终端的一个快照。用法是固定的三段：

```rust
state.update(term.raw())?;          // 从终端刷新
state.for_each_row(|row| { ... });  // 在回调里读单元格
```

单元格数据只在 `update` 之后、下一次 `update` 之前有效。所以 `for_each_row` 的设计是「回调里读完，不要存指针」——回调收到的 `Row` 是已经拷贝出来的值，天然不可能持有悬垂引用。

### 按键编码

不自己拼 `\x1b[A`。把按键、修饰键、字符交给 `ghostty_key_encoder_encode`，它会读终端当前模式（application cursor keys、modifyOtherKeys、kitty 键盘协议），输出正确的序列。这样终端跑 `vim` 或 `htop` 时方向键不会错。

## PTY 层

ConPTY 的读和写各一个线程，中间用 channel。界面线程只做 `try_recv`，永远不会阻塞在管道上。

写也一样：`write` 把字节丢进 channel 就返回。终端程序输出快时，界面不会被写操作拖住。

## 界面层

### 绘制

终端网格不是布局问题：每格一样大，不换行，原点就是元素左上角。所以整块用一个自定义 `Element` 画，三个阶段：

- `request_layout`：声明填满父容器。**不设 `min_size`**——那会把网格撑到比容器大，画到窗格外。
- `prepaint`：从实际 bounds 算出能放几列几行，写进一个 `Rc<Cell<(u16,u16)>>` 给外壳。这是唯一知道真实尺寸的地方。
- `paint`：三遍。先画所有单元格背景（否则相邻格的字会压在后面的背景上），再画字形，最后画下划线、删除线、光标、滚动条。

光标用 `paint_quad` 画实心块、竖线或下划线，按终端报告的 `CursorStyle` 分支。

### 尺寸反馈

窗格尺寸有个循环依赖：PTY 要知道几列几行，而这个数只能从渲染后的 bounds 得到。

解法是让 `prepaint` 把实测的格数写进 `Cell`，`render` 下一帧读它并调用 `resize`。用 `Cell` 而不是 `Signal`，因为 `prepaint` 发生在渲染中，此时触发响应式更新会 panic。

### 分屏

布局是一棵树：

```rust
enum Layout {
    Leaf(u64),
    Split { axis: Axis, ratio: f32, first: Box<Layout>, second: Box<Layout> },
}
```

`Leaf` 存窗格 id，窗格本体在 `BTreeMap<u64, Pane>` 里——用 map 而不是 vec，删除一个窗格不会让其他窗格的 id 失效。

渲染时递归展开：`Split` 变成一个 `flex_row` 或 `flex_col` 容器，两个子节点各占 `flex_basis(ratio)`。让 flex 引擎分配空间，而不是自己算像素宽度，这样嵌套分屏也能正确分摊。

导航（`Alt+方向`）按几何位置算：在所有窗格矩形里找与当前窗格在同一行/列、且位于指定方向、距离最近的。按几何而不是按树，因为树的结构和用户看到的方位不一定一致。

### 侧栏

标题栏不再画标签。左侧一栏就是标签栏：一个标签占一行，标签里只有一个窗格时这一行就是那个标签；有多个窗格时它变成一个组，组头是标签，下面是缩进的窗格行。每行都能点——点标签行切过去，点窗格行切过去并聚焦它，和点窗格本身是同一条路径，所以两边永远不会不一致。新建标签的加号在栏头，关闭标签的叉只出现在当前标签行上：关哪个是明确的，也不会把一列叉铺成一片。

状态没有问任何程序，只看两件事：进程是否还在（`exit_code`），以及最后一次输出是多少毫秒之前。约一秒内有过输出就是「输出中」，否则「空闲」，进程没了是「已退出」。这样 shell、构建、测试监听器都能被正确描述，而不需要它们配合上报。

列表不能隐藏：它是窗口里唯一的标签入口，藏起来就没有退路。它默认是窄条，宽窄只由用户决定——点标题栏左上角的应用标记、按 `Ctrl+Shift+B`，或者拖它的右边缘；分开窗格不会自动把它撑开。窄条是导航，不是内容，没有理由去抢终端的宽度。

窄条用一个胶囊装一个标签：胶囊的描边就是标签的边界。没轮到的标签是普通描边加半档 `muted` 的淡底（整档 `muted` 是行的悬停色，静态表面不能借用），当前标签换成强调色描边——激活状态靠边框说，不靠填充。胶囊里保持同样的两级：多窗格的标签先是一个小的标签字，下面才是它的窗格块；单窗格的标签就是一块，因为它就是一个地方。块里放名字的第一个字，两个窗格首字相同时改用序号，否则一列 `P P` 又退回了原来的「一堆一样的点」。窄条里不画状态点：五个像素的点在这个尺寸上是要找的芝麻，状态改由块的底色说——输出中借强调色的淡底，已退出借危险色，空闲没有底色；选中的块是白底。新建标签的加号是一个同样大小的空胶囊，所以「再加一个」和已有的标签用的是同一个形状。拖着右边缘往下过 118px 就进入窄条，`Ctrl+Shift+B` 在窄条和上次的宽度之间切换：折叠不是另一个模式，而是宽度的一个取值。

右边缘的抓手和窗格之间的分隔是同一种东西：3px 的强调色胶囊，26px 长，指针进入边缘带时才出现，拖动期间一直亮着。整个窗口里可拖的边只有这两处，看上去也该是一回事。

侧栏和窗格区共用一条 10px 的外沿：栏顶和卡片顶、栏底和卡片底、卡片左侧和卡片上侧，量的都是同一个 10px。区域自己的边距先成立——列表行还有 6px 内缩，那是列表内部的事，不再为了让「行到卡片」等于「卡片到卡片」而把卡片往左挤：卡片离栏 4px、离顶栏 10px 的时候，内容在自己的区域里是偏的，眼睛先看到的是这个。

标签全关掉时，空列表给的不是一句说明，而是一行「新建终端」——空列表唯一还能告诉人的，就是下一个从哪儿来。

### 安装提示

还没安装的副本在启动时，标题栏下面会出现一条可关闭的提示带：一句话说明它还没装到这台电脑，右边是「安装」和「稍后」，安装失败的原因也留在同一条带里。它不是对话框——安装是一个提议，一个不接受就挡住网格的终端不算终端。已经安装过（安装位置有副本）就不再出现；按「稍后」只关掉这一次。

标题栏最左边的应用标记和侧栏共用一条 14px 的左边线：列表展开时它和「标签」的左缘对齐；窄条时标记框和窄条块都是 28px 宽，同一个数字正好让它落在窄条的中线上。一处对齐，两种宽度，不用为窄条再记一个偏移。它同时是列表的开关：按一下展开，再按一下收回——图标就在它要开的那一栏旁边，不用另找一个按钮。它也不再是窗体的拖动区：一个会移动窗口的控件不是控件。

### 焦点

终端是窗口里唯一可聚焦的东西。每次 `render` 检查焦点，被抢走就抢回来——点标签、点分屏按钮之后，键盘必须继续进终端。

窗格之间的焦点靠「变淡」而不是描边：没有键盘的卡片蒙一层与底色同色的薄雾。这样切换焦点时没有任何像素位移，也不会在已经很密的终端界面上再加一圈线。

### 定时轮询

PTY 没有事件通知，所以用一个 16ms 的定时器轮询。轮询只在有变化时 `notify`，空闲时进程是安静的。

## 布局

界面只有两层东西：**外壳**和**卡片**。左侧还有一栏**列表**（见下），但它是外壳的一部分，不是第三层。

外壳是标题栏和卡片之间的空隙，用 `bg_soft`；卡片是终端本身，用 `bg`，外加一条 `border` 描边。分成多个窗格时，每个窗格是一张卡片，卡片之间留 10px 的外壳色，角落是 12px 圆角。

那条描边是必须的。白卡片放在近白的外壳上，没有边缘的话两块面会融成一片，中间的间隙就没人看得见——「间隔」这个概念根本传不出去。有了描边，两条边加中间的空隙自己就说明了「这是两个东西」。

所以分隔区**不画线**。试过在间隙中间再加一条线，结果是「卡片边、分隔线、卡片边」三条规则挤在十几个像素里，读起来像栅栏而不是分区。分隔区平时是空的，只有指针停上去才浮出一小段强调色的手柄，说明它能拖——这和侧栏边缘用的是同一个手势。

窗格多于一个时，每张卡片顶部多一行 32px 的窗格头：一个状态点、一个名字，右边是悬停才出现的分屏 / 缩放 / 关闭。单窗格时不显示——侧栏已经说了它是谁，再写一遍等于用 32px 什么也没说。这条规矩决定了整个界面的密度：**chrome 随复杂度增长**。

焦点不画边框。没有键盘的窗格整体变淡：卡片抬起一点、文字上面蒙一层与底色同色的薄雾。相比一圈描边，它更安静，而且不会在切换时移动任何一个像素。强调色只留给标题栏的应用标记、窗格头上的状态点，和悬停中的可拖动间隙。

缩放是临时的：`zoomed` 只影响渲染，布局树不动，所以放开缩放时每个窗格回到原来的位置和比例。

## 配色

ANSI 16 色和默认前景/背景通过 `ghostty_terminal_set` 注入解析器，而不是只在绘制时替换。这样跑 `curl` 或 `ls --color` 时，程序查询颜色得到的值和屏幕上的值一致。

界面用一套自己的 token（`crates/myterm/src/palette.rs`）：四个表面（`bg` / `bg_soft` / `surface` / `pill`）、三档文字（`text` / `text_2` / `text_3`）、一条描边（`stroke`），加一个青柠色强调（`brand`）。两层含义：

- **表面**：网格用最深的 `bg`，外壳（标题栏、窗格之间的空隙）用 `bg_soft`，抬起来的东西（选中的标签）用 `surface`。窗格因此像放在一层浅色底上的卡片，而不是几块刚好停住的矩形。
- **强调**：`brand` 只给三处用——标题栏的应用标记、键盘所在的窗格描边、可拖动的空隙悬停。强调色用在哪里，就说明哪里是「当前」的。

这些 token 会写进组件主题（`Theme::update` 覆盖 `ThemeColor`），所以库里那些现成控件也自动落在同一套颜色上，不必逐个改。深浅两套的结构完全一样，只是值不同，所以同一个界面在两种模式下读起来是同一个界面。ANSI 16 色也按这套色系重新调过，终端里的红绿黄蓝和外壳不打架。

## 测试

- `vt/tests/api.rs`：跑真实库。喂 VT 字节，读回单元格、光标、颜色、滚动条、选区、按键编码。10 个测试覆盖了绑定的每个易错点——结构体布局错、枚举值错、`size` 没填，都会在这里失败。
- `myterm/src/layout.rs`：6 个测试覆盖分屏。切分不留缝、奇数尺寸不丢行、删除提升兄弟、导航按几何。

这些测试不需要窗口，也不依赖 GPU。

## 更新

发布走 GitHub Releases：`v*` 标签触发 CI 构建，把 `myterm.exe` 附在 release 上。应用启动后查一次最新版本，比对标签里的版本号。

四点值得写下来：

- **不查 API，查重定向**。`api.github.com` 对未认证请求限流 60 次/小时/IP，重启几次就用完了——第一次实现正是这样，开发中途就开始报 403。`github.com/.../releases/latest` 会 302 到 tag 页面，这条路径不限流，也不需要凭据，而它携带的信息（tag 名）刚好够用。
- **比较是逐段数字**，缺失的段按 0 算，所以 `0.2` 比 `0.1.9` 新。标签解析不了就当作「没有新版本」——拒绝更新是安全的方向。
- **404 不算错误**。仓库还没有发布过任何 release 时 GitHub 返回 404，这和网络故障是两件事。前者什么都不显示，后者才在标题栏说明。
- **替换要等进程退出**。Windows 不允许覆盖正在运行的可执行文件，所以下载写到同目录的 `myterm.new.exe`，再由一个短命脚本在进程结束后搬过去并重启。下载完成前会检查文件头是不是 `MZ`，避免把重定向后的错误页当成程序写下去。

`ureq` 的 body 读法有个坑：`as_reader().read_to_end()` 在这里永不返回，reader 不知道 body 在哪结束。要用 `read_to_vec()`，而它的默认上限是 10 MB——小于这个二进制，所以显式抬高到 256 MB。

更新只在启动时查一次，没有轮询，也没有后台常驻。失败会留在徽章上并且可以点重试。
