# myterm 设计

一个 Windows 终端。目标是把「终端」这件事做对：VT 解析交给成熟的库，界面用现代的 Rust 框架，其余全部是自己的代码，且每一层都能单独测试。

## 为什么这样分层

终端应用有三个几乎无关的问题：

1. **字节到网格**。ANSI 序列、宽字符、回滚、选区、按键编码——这是 VT 解析器的工作，细节多且容易出错。
2. **网格到像素**。每个单元格的位置、颜色、装饰线、光标形状。
3. **应用外壳**。工作区、分屏、快捷键、配置。

把三者混在一起，任何一处改动都会牵连另外两处。所以分成四个 crate，依赖严格向下：

```
app ──► pty
 │       ▲
 └────► vt ──► vt-sys
```

`vt-sys` 是唯一出现 `unsafe extern "C"` 的地方；`vt` 把指针所有权、错误码、颜色类型全部包装成值；`pty` 只负责进程和管道；`app` 只做界面。这条边界让「解析器崩了」和「界面画错了」永远不会混在同一个栈里。

## VT 层

### 为什么用官方 C API

之前用第三方 Rust 封装，它锁在一个 pre-1.0 的 commit 上，封装本身有近两万行。官方 1.0.0 提供了稳定 ABI 和版本承诺，代价是要自己写绑定。

绑定是手写的：本机没有 `libclang`，`bindgen` 不可用。手写反而更可控——只声明真正用到的约 40 个函数，每个常量都对着头文件核对过。

### 静态库

`libghostty-vt` 用 Zig 构建，官方不发 Windows 包。做法是在 1.0.0 源码上跑：

```sh
zig build -Demit-lib-vt -Doptimize=ReleaseFast
```

把 `zig-out/lib/ghostty-vt-static.lib`（12.5 MB）提交进仓库。这样构建机不需要 Zig、不需要网络、不需要 CMake。`build.rs` 只做两件事：检查文件在不在，然后告诉 cargo 链接它。

### sized struct

C API 里所有输出结构体第一个字段是 `size_t size`，库用它判断调用方编译时的结构体版本。Rust 侧不能靠 `derive(Default)`——那会把 `size` 置零，库会拒绝写入。每个这样的结构体都手写 `Default`，显式填 `size_of::<Self>()`。

这个坑在写测试时立刻暴露了：光标位置读出来永远是 0，因为 `GhosttyRenderStateCursor::default()` 的 `size` 是 0。

### 渲染状态

`RenderState` 是终端的一个快照。用法是固定的三段：

```rust
state.update(term.raw())?;          // 从终端刷新
state.for_each_row(|row| { ... });  // 在回调里读单元格
```

单元格数据只在 `update` 之后、下一次 `update` 之前有效。所以 `for_each_row` 的设计是「回调里读完，不要存指针」——回调收到的 `Row` 是已经拷贝出来的值，天然不可能持有悬垂引用。

### 按键编码

不自己拼 `\x1b[A`。把按键、修饰键、字符交给 `ghostty_key_encoder_encode`，它会读终端当前模式（application cursor keys、modifyOtherKeys、kitty 键盘协议），输出正确的序列。这样终端跑 `vim` 或 `htop` 时方向键不会错。

## PTY 层

ConPTY 的读和写各一个线程，中间用 channel。界面线程只做 `try_recv`，永远不会阻塞在管道上。

写也一样：`write` 把字节丢进 channel 就返回。终端程序输出快时，界面不会被写操作拖住。

## 界面层

### 绘制

终端网格不是布局问题：每格一样大，不换行，原点就是元素左上角。所以整块用一个自定义 `Element` 画，三个阶段：

- `request_layout`：声明填满父容器。**不设 `min_size`**——那会把网格撑到比容器大，画到窗格外。
- `prepaint`：从实际 bounds 算出能放几列几行，写进一个 `Rc<Cell<(u16,u16)>>` 给外壳。这是唯一知道真实尺寸的地方。
- `paint`：三遍。先画所有单元格背景（否则相邻格的字会压在后面的背景上），再画字形，最后画下划线、删除线、光标、滚动条。

光标用 `paint_quad` 画实心块、竖线或下划线，按终端报告的 `CursorStyle` 分支。

### 尺寸反馈

窗格尺寸有个循环依赖：PTY 要知道几列几行，而这个数只能从渲染后的 bounds 得到。

解法是让 `prepaint` 把实测的格数写进 `Cell`，`render` 下一帧读它并调用 `resize`。用 `Cell` 而不是 `Signal`，因为 `prepaint` 发生在渲染中，此时触发响应式更新会 panic。

### 分屏

布局是一棵树：

```rust
enum Layout {
    Leaf(u64),
    Split { axis: Axis, ratio: f32, first: Box<Layout>, second: Box<Layout> },
}
```

`Leaf` 存窗格 id，窗格本体在 `BTreeMap<u64, Pane>` 里——用 map 而不是 vec，删除一个窗格不会让其他窗格的 id 失效。

渲染时递归展开：`Split` 变成一个 `flex_row` 或 `flex_col` 容器，两个子节点各占 `flex_basis(ratio)`。让 flex 引擎分配空间，而不是自己算像素宽度，这样嵌套分屏也能正确分摊。

导航（`Alt+方向`）按几何位置算：在所有窗格矩形里找与当前窗格在同一行/列、且位于指定方向、距离最近的。按几何而不是按树，因为树的结构和用户看到的方位不一定一致。

### 工作区栏

顶栏不再画标签。左侧一栏贯穿整个窗口的高度，就是工作区栏——窗口里唯一的工作区入口，
藏起来就没有退路，所以它不能被关掉，只有两个宽度。

**两档。** 展开时一行一个工作区：组头带布局字形、名字、窗格数与关闭叉，多窗格的组头下有窗格行，
每行是状态点、名字、shell 报上来的目录。窄条时一个工作区一个方块——当前工作区整块带底色，
每个窗格一枚 30px 的块，右上角一枚状态点，首字按状态取色。宽度只由用户决定：点应用标记、
按 `Ctrl+Shift+B`、或者拖右边缘。分屏不会把它撑开，窄条是导航，不是内容。

**状态不问任何程序**，只看两件事：进程是否还在（`exit_code`），以及最后一次输出是多少毫秒之前。
约一秒内有过输出就是「输出中」，否则「空闲」，进程没了是「已退出」。形状先于颜色：实心圆、空心圆、
方块。窄条里再加一层——字的颜色也跟着状态走。

**目录从 OSC 标题来。** shell 把标题设成路径时，去掉用户主目录前缀写成 `~/…`；设成 exe 路径时
（PowerShell 默认如此）这一行留空。没有进程目录查询：ConPTY 下那件事不可靠，用一种看起来像答案的
猜测代替它更糟。

右边缘的抓手和窗格之间的分隔是同一种东西：3px 的强调色胶囊，26px 长，指针进入边缘带时才出现。

### 安装提示

还没安装的副本在启动时，标题栏下面会出现一条可关闭的提示带：一句话说明它还没装到这台电脑，右边是「安装」和「稍后」，安装失败的原因也留在同一条带里。它不是对话框——安装是一个提议，一个不接受就挡住网格的终端不算终端。已经安装过（安装位置有副本）就不再出现；按「稍后」只关掉这一次。

标题栏最左边的应用标记和侧栏共用一条 14px 的左边线：列表展开时它和第一行的左缘对齐；窄条时标记框和窄条块都是 28px 宽，同一个数字正好让它落在窄条的中线上。一处对齐，两种宽度，不用为窄条再记一个偏移。它同时是列表的开关：按一下展开，再按一下收回——图标就在它要开的那一栏旁边，不用另找一个按钮。它也不再是窗体的拖动区：一个会移动窗口的控件不是控件。

### 焦点

点击窗格会把键盘交给终端。查找、命令面板和重命名输入框可以保有自己的焦点。
当前窗格用更亮的粗体标题标记。分屏时再加一圈淡强调色边缘光，窗格内部仍透出整窗渐变，
所有窗格的终端输出保持同样的对比度。

### shell 集成

目录和分支都来自 shell 自己报的 OSC 7。PowerShell 默认不报，所以这两处在它下面一直是空的。

设置里有一个显式的开关：打开后新窗格用包装过的提示符启动——保存原来的 `prompt` 函数，写一段
OSC 7 再调用它。默认关闭，因为它改写的是用户的提示符；也只对之后新建的窗格生效，正在跑的 shell
没法从外部改提示符，为一项设置重启它会丢掉它正在做的事。

只覆盖 PowerShell。`cmd` 没有可包装的提示符函数，`wsl` 跑的是另一个 shell，那是它自己的事。

### 设置

设置是**工作区右侧的一列**，不是浮在终端上的抽屉。抽屉的代价是实打实的：它用遮罩压暗整个工作
区，盖住窗格卡片的圆角，还挡住终端上的点击——而它存在的理由恰恰是「改字号时能看着终端一起变」。

作为一列，窗格在左边收窄，保持完整的高度和圆角；顶栏横跨两者，所以工作区的名字和命令入口不会
被挤。改任何一项，左边的网格当场跟着变。

### 分支

窗格头在目录后面带一枚 `· main`。它读 `.git/HEAD` 并向上找几层，不调用 git——为了一个词每两秒
起一个进程不划算。分支按**目录**缓存，而不是按窗格：同一个检出里的两个窗格只走一次。每两秒重建
一次，且只针对屏幕上真正出现的目录。

### 工作区的名字

一个工作区是一个地方，不是一个进程。新建时它的名字跟着第一个 shell 走（所以新窗口写 `pwsh`），
重命名之后就停下来：一个叫「日志」的工作区不该因为里面跑起了构建就改叫 `cargo`。
名字在右键菜单和命令面板里都能改。

### 命令面板

两组：**命令**（窗口能做什么）和**会话**（shell 在哪）。会话行是**一个窗格**，不是
一个工作区——工作区不是能落地的目标，键盘总归要进某个窗格，让应用替你选是替你做决定。行的右侧
写 `工作区 · 目录`，所以「记得它在日志里」和「记得它在 ~/srv」两种记法都能搜到。

### 查找

查找走库自己的搜索接口，覆盖回滚区与备用屏：这曾经是「查找只覆盖当前屏幕」那条已知限制，
后来发现绑定其实已经在 `vt-sys` 里，只是没人驱动它。现在 `vt::Search` 包住它，`Session` 在查找
打开期间持有一个，每 16ms 推进一点（搜索是增量的，不阻塞帧）。

- 输入即搜，跳到最新一处；`Enter` / `Shift+Enter`（或 `F3`）在命中之间走，库会把视口滚到那一条。
- 计数是整台终端的，不是一屏的。
- 换行之后要先 `feed` 再取视口命中：缓存的视口命中描述的是滚动之前的屏幕，不喂就会把高亮
  画在上一屏的位置上。

### 定时轮询

PTY 没有事件通知，所以用一个 16ms 的定时器轮询。轮询只在有变化时 `notify`，空闲时进程是安静的。

## 布局

标题栏、工作区栏、设置栏和默认终端窗格共享整窗渐变。分屏之间留出 8px 间距，当前窗格的边缘光沿 10px 圆角绘制。

分隔区**不画线**。试过在间隙中间再加一条线，结果是「卡片边、分隔线、卡片边」三条规则挤在十几个
像素里，读起来像栅栏而不是分区。分隔区平时是空的，只有指针停上去才浮出一小段强调色的手柄。

浮层同理：菜单、命令面板、对话框、关于卡、toast 全部只有底色和阴影，没有描边。设置不是浮层，
它是工作区右侧的一列（见下）。菜单里
的分隔符是一段留白，不是一条线；设置和快捷键的行靠行距分开；对话框的次要按钮是浅底而不是描边按钮。
滚动条平时是透明的，指针进入那一块才显形——一条常驻的滑块在无线的界面里就是最后一条硬线。

窗格多于一个时，每张卡片顶部多一行 30px 的窗格头：状态、名字、（多窗格时的）序号、
`目录 · 分支`，右边是分屏 / 缩放 / 关闭。单窗格时不显示——顶栏已经说了它是谁。这条规矩决定了
整个界面的密度：**chrome 随复杂度增长**。窗格头的动作在持有键盘的卡片上常显，其余卡片悬停出现；
缩放中的那一枚按钮带强调底，说明它正处在那个模式里。

缩放是临时的：`zoomed` 只影响渲染，布局树不动，所以放开缩放时每个窗格回到原来的位置和比例。
缩放期间状态条出现，写明 `Esc 退出`。

顶栏 44px：工作区名、目录、`Ctrl+K` 的命令入口、分屏与新建、应用菜单、窗口按钮。命令入口是鼠标
用户唯一找得到的「全部功能」，所以它是一条带文字的输入框，不是一个图标。

状态条 26px，**只在有话要说时出现**，而它只有一件事要说：正在缩放（`已缩放 · Esc 退出`）。
后台有新输出由侧栏行上的点说，可下载的更新由顶栏的徽章说——同一件事说两遍，这条就会几乎常驻，
而常驻正是它要避免的。

## 配色

ANSI 16 色和默认前景/背景通过 `ghostty_terminal_set` 注入解析器，而不是只在绘制时替换。这样跑
`curl` 或 `ls --color` 时，程序查询颜色得到的值和屏幕上的值一致。

Sixel DCS 数据在进入 libghostty-vt 之前由 `crates/myterm/src/sixel.rs` 提取并解码。结果以 RGBA
图片加入现有渲染路径，按照光标所在单元格放置，并随窗格边界裁剪。Kitty 图形仍由 libghostty-vt 管理。
vt 层在 DA1 查询中声明 Sixel 能力，让图形程序可以据此选择协议。

界面颜色由 `crates/myterm/src/palette.rs` 统一定义。浅色与深色主题各自提供文字、表面和状态颜色。
整窗渐变使用当前强调色的色相，连续延伸到标题栏、侧栏、设置栏和默认终端窗格。
终端程序显式指定窗格或字符格的底色时，会显示程序指定的颜色。

- **选色**：设置 → 外观提供两行共八种有名称的色板。选中项用底色、边框和字重一起标识。
- **配置**：`accent` 支持青柠 `lime`（默认）、琥珀 `amber`、珊瑚 `coral`、玫瑰 `rose`、
  薄荷 `mint`、天蓝 `sky`、靛蓝 `indigo` 和紫罗兰 `violet`。
- **应用范围**：强调色同时更新渐变、浮层底色、选中状态、焦点窗格边缘光和终端光标。
  主题继续决定界面的明暗和终端 ANSI 16 色。

这些 token 会写进组件主题（`Theme::update` 覆盖 `ThemeColor`），所以库里那些现成控件也自动落在
同一套颜色上。

## 测试

- `vt/tests/api.rs`：跑真实库。喂 VT 字节，读回单元格、光标、颜色、滚动条、选区、按键编码。10 个测试覆盖了绑定的每个易错点——结构体布局错、枚举值错、`size` 没填，都会在这里失败。
- `myterm/src/layout.rs`：6 个测试覆盖分屏。切分不留缝、奇数尺寸不丢行、删除提升兄弟、导航按几何。

这些测试不需要窗口，也不依赖 GPU。

## 更新

发布走 GitHub Releases：`v*` 标签触发 CI 构建，把 `myterm.exe` 附在 release 上。应用启动后查一次最新版本，比对标签里的版本号。

四点值得写下来：

- **不查 API，查重定向**。`api.github.com` 对未认证请求限流 60 次/小时/IP，重启几次就用完了——第一次实现正是这样，开发中途就开始报 403。`github.com/.../releases/latest` 会 302 到 tag 页面，这条路径不限流，也不需要凭据，而它携带的信息（tag 名）刚好够用。
- **比较是逐段数字**，缺失的段按 0 算，所以 `0.2` 比 `0.1.9` 新。标签解析不了就当作「没有新版本」——拒绝更新是安全的方向。
- **404 不算错误**。仓库还没有发布过任何 release 时 GitHub 返回 404，这和网络故障是两件事。前者什么都不显示，后者才在标题栏说明。
- **替换要等进程退出**。Windows 不允许覆盖正在运行的可执行文件，所以下载写到同目录的 `myterm.new.exe`，再由一个短命脚本在进程结束后搬过去并重启。下载完成前会检查文件头是不是 `MZ`，避免把重定向后的错误页当成程序写下去。

`ureq` 的 body 读法有个坑：`as_reader().read_to_end()` 在这里永不返回，reader 不知道 body 在哪结束。要用 `read_to_vec()`，而它的默认上限是 10 MB——小于这个二进制，所以显式抬高到 256 MB。

更新只在启动时查一次，没有轮询，也没有后台常驻。失败会留在徽章上并且可以点重试。
